사업계획서 자체를 기사화하지 않는다. 사업계획서는 **조사해야 할 기술·산업 영역을 정하는 기준**으로만 사용한다.

## 3. 해외자료 우선 원칙
국내 자료는 가능한 한 사용하지 않는다.
우선 조사 국가는 **미국 · 일본 · 대만 · EU · 중국 · 러시아**로 한다. 필요하면 기타 국가의 중요한 기술도 포함한다.

자료 우선순위:
**① 기업 공식자료 ② 연구기관·대학 ③ 정부·공공기관 ④ 학회·논문 ⑤ 전문 산업매체 ⑥ 일반 언론**

뉴스에서 기술을 발견하더라도 가능하면 기업·연구기관 등의 원출처까지 역추적한다.
한국 자료는 한국과의 비교가 필요하거나 해외 원문 확인이 불가능한 경우에만 보조적으로 사용한다.

## 4. 최신성 기준
기사 작성일 기준 우선순위는 **최근 7일 → 최근 30일 → 최근 3개월**이다.
최근 자료만으로 설명이 어려우면 과거 자료를 기술 배경으로 사용할 수 있다.

반드시 **자료 게시일과 실제 사건·발표일을 구분**한다. 오래된 사건을 최근 기사에서 다시 언급했다는 이유만으로 최신 변화처럼 쓰지 않는다.

## 5. 유한 실행 원칙 — 조사 무한루프 금지
기사 생성 작업은 반드시 끝나야 한다.

1. 기존 `k-article` 기사 제목·주제를 확인한다.
2. 1차 조사에서 후보를 수집한다.
3. 적합 후보가 없을 때만 **조사 범위를 1회 확장**한다.
4. 확장 후에도 신규성·근거·사업관련성을 충족하는 주제가 없으면 억지로 작성하지 않는다.
5. 이 경우 **`신규 기사 보류(HOLD)`**로 종료한다.

동일한 검색어를 반복하거나, 적합한 주제가 나올 때까지 무기한 조사하지 않는다.

## 6. 주제 선정 Gate
하루 기사에는 **주제 하나만 선정**한다.

후보는 다음 4축으로 평가한다.
- 신규성
- 기술 중요도
- FAB 운영/사업 관련성
- 근거 신뢰도

다음 조건은 필수 Gate다.
- FAB 운영 또는 관련 사업과 직접 연결된다.
- 기존 기사와 본질적으로 같은 내용이 아니다.
- 최신 변화 또는 명확한 후속 진전이 있다.
- 확인 가능한 출처가 있다.

Gate를 통과한 후보 중 가장 가치가 높은 하나를 선택한다.

## 7. 근거(Evidence) Gate
기사의 핵심 주장은 출처로 검증할 수 있어야 한다.

- 특정 기업·제품·기술의 존재와 기능을 주장할 때는 **1차 자료 1개 이상**을 우선 확보한다.
- 가능하면 독립적인 해외 자료 1개 이상으로 교차 확인한다.
- 기업 발표 하나만 존재하면 `회사 발표에 따르면` 등으로 출처 성격을 명시한다.
- 수치·성능·비율·금액·일정은 출처와 기준 시점을 확인한다.
- 전망·예측·추정은 사실처럼 단정하지 않는다.
- 확인되지 않은 제품명·서비스명·기업 관계를 만들어내지 않는다.

근거가 약하면 문장을 약화하거나 제거한다. 근거 부족을 상상으로 메우지 않는다.

## 8. 중복 방지
기존 `k-article` 기사 제목뿐 아니라 **핵심 주제·기술·기업·적용사례**까지 확인한다.

같은 기술이라도 다음 중 하나가 명확하면 후속기사로 허용한다.
- 새로운 제품 또는 서비스
- 새로운 고객/적용 사례
- 성능·공정·운영 방식의 의미 있는 진전
- 규제·정책·공급망 변화

후속기사라면 기존 기사와 무엇이 달라졌는지 본문에서 드러나야 한다.

## 13. 대표이미지 — 빠른 종료 원칙
기사마다 대표이미지 1장을 목표로 한다.
이미지는 기술 원리를 모두 설명하는 도식이 아니라 **기사 주제와 연결된 실제 산업현장 대표사진**이면 충분하다.

기본 기준:
- 사실적인 산업현장 사진형
- 16:9
- 게시용 1200×675 JPG
- 기사 핵심 장면 하나
- 인포그래픽·포스터·뉴스페이지 금지
- 기사 제목·차트·표·화살표·기업 로고 금지
- AI 제작 고지는 이미지 세부 규칙에 따라 정확히 적용

생성은 기본 1회, 명백한 오류 시에만 1회 추가한다. **한 기사당 최대 2회**다.
상세 규칙은 `chatgpt/K-ARTICLE-IMAGE-RULES.md` v2.4 이상을 필수 적용한다.

## 14. 이미지 파일 버전 — 동일 바이너리 중복 금지
기존 파일을 덮어쓰지 않는다.

- 최초: `YYMMDD.AutoGen.기사제목.v1.jpg`
- 수정: `...v2.jpg`
- 재수정: `...v3.jpg`

저장 전 동일 기사 최고 `vN`을 확인한다.

**중요:** 새 이미지의 바이너리/SHA가 현재 최고 버전과 동일하면 새 `N+1` 파일을 만들지 않는다. 기존 최고 버전을 그대로 사용한다.
새 바이너리일 때만 `N+1`로 저장한다.
무버전 이미지는 레거시 `v0`로 취급한다.

## 15. GitHub 저장
저장소는 반드시 **`wskimgit/k-article`**, branch는 **`main`**이다.
TXT와 대표 JPG는 repository root에 저장한다.

### TXT
- UTF-8 텍스트로 저장한다.
- 동일 경로가 이미 존재하면 기존 내용과 비교한다.
- 내용이 동일하면 불필요한 update commit을 만들지 않는다.
- 실제 수정이 필요할 때만 업데이트한다.

### JPG
실제 JPEG 바이너리만 저장한다.
`.jpg.b64`, placeholder, Base64 텍스트 파일을 최종 이미지로 저장하지 않는다.

**직접 저장 절차:**
1. 현재 `main` HEAD commit과 base tree를 확인한다.
2. 최종 JPG를 Base64로 `create_blob`한다.
3. **현재 base tree를 유지한 상태로** 새 이미지 경로만 추가한 `create_tree`를 만든다.
4. 현재 HEAD를 parent로 `create_commit`한다.
5. `update_ref(main)`은 **force 없이 fast-forward**로 수행한다.
6. main이 중간에 변경되어 ref update가 실패하면 최신 HEAD를 다시 읽어 **동일 바이너리로 1회만 재시도**한다.
7. `fetch_file(..., base64)`로 저장 결과를 재검증한다.

### 금지
대표이미지 한 장 저장을 위해 다음을 새로 만들지 않는다.
- GitHub Actions workflow
- trigger 파일
- Base64 조각 파일
- 임시 upload 폴더
- placeholder

정상 이미지 확보 후 저장 실패를 이유로 이미지를 새로 생성하지 않는다.
저장 재시도는 **최대 1회**다.

## 16. K-BIZPOST 연동
운영 구조:
**ChatGPT 기사 생성 → k-article 저장 → NAS의 egtech.php가 k-article 확인 → 신규/변경 TXT 및 vN 이미지 파일을 NAS `egTEC` 폴더에 저장 → egtech.php가 기사별 최고 이미지 버전을 자동 선택하여 표시**

K-BIZPOST 데이터 폴더: `/egTEC/`
운영 페이지: `egtech.php`

표시 규칙:
1. TXT 논리 stem 기준으로 이미지 후보 검색
2. `vN` 중 가장 높은 N 표시
3. 버전 파일이 없을 때만 무버전 레거시를 `v0` fallback으로 사용
4. 같은 버전이면 `jpg → jpeg → png → webp → gif`
5. 필요 시 `mtime-size` query로 캐시 방지

## 17. GitHub→NAS 동기화 원칙
GitHub `k-article`은 원본 저장소, NAS는 배포본이다.

- 새 TXT와 새 `vN` 이미지를 내려받는다.
- 신규/변경 파일만 반영한다.
- SHA 또는 수정 여부를 비교한다.
- 과거 이미지 버전은 자동 삭제하지 않는다.
- GitHub 파일 삭제를 NAS 자동 삭제로 연결하지 않는다.
- 동기화 실패 시 기존 NAS 기사를 삭제하지 않는다.
- GitHub 일시 장애 시 기존 서비스는 계속 동작해야 한다.
- 동일 파일을 매 접속마다 반복 다운로드하지 않는다.

## 18. ERRC 검증 — 1회 원칙
게시·저장 전에 ERRC를 **1회** 수행한다.

### E — Error Check
- 기업·제품·기술명 정확성
- 날짜와 실제 사건일 정확성
- 기술 설명 오류 여부
- 핵심 주장과 원출처 일치
- 존재하지 않는 제품·서비스 생성 여부
- TXT/JPG 파일명 규칙
- 이미지 버전 및 동일 SHA 중복 방지

### R — Relevance / Redundancy
- FAB 운영 플랫폼 사업과 직접 관련되는가
- 단순 반도체 일반 뉴스가 아닌가
- 기존 기사와 본질적으로 중복되지 않는가
- 한 기사 한 주제 원칙을 유지하는가

### R — Recency / Reliability
- 최신 해외자료를 충분히 확인했는가
- 1차 자료가 존재하는가
- 게시일과 실제 사건일을 혼동하지 않았는가
- 오래된 정보를 최신처럼 사용하지 않았는가
- 가능하면 독립 해외자료로 교차 확인했는가

### C — Consistency
**기사 제목 ↔ 본문 ↔ 날짜 ↔ TXT 파일명 ↔ JPG 논리 stem ↔ 이미지 버전 ↔ GitHub 위치 ↔ AI 고지**를 대조한다.

ERRC 실패 시 해당 오류를 1회 수정하고 재검증한다. 같은 이유로 무한 반복하지 않는다.

## 19. 저장 후 검증
### TXT
1. 정확한 경로 존재
2. UTF-8 내용 정상
3. 파일명 정상
4. 원격 내용이 최종 본문과 일치

### JPG
1. 최신 `.vN.jpg` 존재 또는 동일 SHA 기존 최고 버전 재사용
2. Base64 재조회 성공
3. JPEG 시작 시그니처 `FF D8`
4. 가능하면 종료 시그니처 `FF D9` 또는 정상 decode
5. 1200×675
6. blob SHA 확인
7. TXT와 이미지 논리 stem 일치
8. `.jpg.b64`, chunk, placeholder가 새 최종 산출물로 남지 않음

검증은 1회 수행한다. 저장 오류만 동일 데이터로 1회 재시도한다.

## 20. 완료 상태
### COMPLETE
TXT와 JPG가 저장·검증 성공했거나, 동일 SHA의 기존 최고 이미지 버전을 정상 재사용한 경우:

**YYYY.MM.DD 기사 생성 완료**
- 주제
- 기사 파일명
- 이미지 파일명
- 저장소 `wskimgit/k-article`
- ERRC: PASS

### PARTIAL
TXT 성공, 이미지 생성 또는 저장 실패:
`기사 저장 성공 / 이미지 생성 또는 저장 실패`

추가 재생성·추가 우회 저장을 계속하지 않는다.

### HOLD
두 차례의 제한된 조사 범위 안에서 신규성·근거·사업관련성을 충족하는 주제가 없을 때:
`신규 기사 보류 / 적합 주제 없음`

### ERROR
TXT 자체를 안전하게 저장·검증하지 못한 경우:
`기사 생성 실패 / 저장 오류`

실패 원인을 짧게 남기고 종료한다.

## 21. 핵심 운영원칙
1. **좋은 주제가 있을 때만 쓴다.**
2. **조사 확장은 최대 1회다.**
3. **근거 없는 내용을 만들지 않는다.**
4. **대표이미지는 최대 2회 생성한다.**
5. **이미지 저장 재시도는 최대 1회다.**
6. **저장 실패 때문에 이미지를 재생성하지 않는다.**
7. **동일 SHA 이미지는 새 버전으로 중복 저장하지 않는다.**
8. **GitHub main은 force update하지 않는다.**
9. **GitHub Actions·trigger·Base64 chunk 우회 저장을 새로 만들지 않는다.**
10. **COMPLETE / PARTIAL / HOLD / ERROR 중 하나로 반드시 종료한다.**

장기간 누적된 `k-article`이 반도체 FAB 운영 플랫폼의 기술·산업 동향 데이터베이스가 되도록 한다.
