# K-ARTICLE 대표이미지 품질·저장·차별화 규칙 v2.2 — FROZEN

기준일: 2026-08-15
상태: FROZEN / K-ARTICLE-RULES에 대한 필수 이미지 규칙

## 1. 이미지 제작 품질
1. 대표이미지는 반드시 고품질 생성형 이미지 모델(image generation)을 사용해 제작한다.
2. Python/PIL 도형 조합, 저해상도 합성, 단순 인포그래픽 방식으로 대표이미지를 새로 그리지 않는다.
3. 기본 형식은 사실적인 산업 현장 사진형 이미지로 한다. 기사 핵심 장면 하나만 표현한다.
4. 기사 제목, 통계, 차트, 표, 기업 로고, 설명 패널을 이미지에 넣지 않는다.
5. 반도체 기사에서는 실제 FAB·클린룸·장비·엔지니어의 구조와 복장이 자연스럽고 전문적으로 보여야 한다.
6. 인물의 손·얼굴·보호복, 장비 구조, 원근, 조명 등 시각적 오류를 저장 전에 확인한다.
7. 원본 이미지는 가능하면 16:9 고해상도로 생성하고, 게시용 JPG는 1200×675로 정규화한다.
8. 우측 하단에만 `생성형 AI 제작 이미지` 문구를 작고 선명하게 표시한다.
9. 이미지가 기사 주제를 직접 설명하지 못하거나 품질이 낮으면 GitHub에 저장하지 않고 재생성한다.

## 2. 대표이미지 차별화·반복 방지 규칙
대표이미지는 최근 기사와 시각적으로 반복되지 않아야 한다. 특히 `두 명의 방진복 인물 + 클린룸 복도 + 장비 앞 정면 구도`가 반복되는 것을 금지한다.

### 2-1. 인원 수 다양화
- 사람을 반드시 넣을 필요는 없다.
- 기사에 따라 **0명 / 1명 / 2명 / 3~5명 / 다수 인원** 중 적절한 구성을 선택한다.
- 최근 이미지가 2명 중심이었다면 다음 이미지는 가능하면 0명·1명·3명 이상 구도를 우선 검토한다.

### 2-2. 복장 다양화
기사의 실제 작업환경에 따라 다음을 선택한다.
- 클린룸 방진복
- 장비 유지보수 작업복
- 헬멧·보안경·안전복
- 연구실 복장
- 관제실·사무환경 복장
- 인물이 없는 장비·웨이퍼·로봇 중심 장면

모든 반도체 기사에서 흰색 방진복을 관성적으로 사용하지 않는다.

### 2-3. 구도 다양화
다음 구도를 순환·조합하여 사용한다.
- 초광각 FAB 전경
- 원거리 생산라인
- 측면·후면 작업 장면
- 장비 내부 또는 챔버 중심
- 웨이퍼·센서·부품·로봇암 클로즈업
- 손과 작업도구 중심의 디테일 샷
- 관제실·원격진단 공간
- 연구실·시험장비 환경
- 물류·MRO·부품 랙·설비실
- 상단·사선·로우앵글 등 비정면 구도

### 2-4. 주제별 시각 모티프 분리
기사 주제에 따라 대표 장면 자체를 바꾼다.
- 장비 엔지니어 부족 → 교육·기술전수·정비·인력 배치
- 예지보전 → 센서·상태진단·알람·장비 건강도
- 공정 제어 AI → 장비 제어·Recipe 검증·APC/FDC·자동화
- 공급망·대체 장비 → 장비 비교·Qualification·테스트 셋업
- MRO·부품 조달 → 부품 랙·교체작업·물류·재고
- Digital Twin → 실제 장비와 가상 모델의 대응 관계
- Robotics/Physical AI → 로봇암·자동이송·무인 작업
- Utility/클린룸 → 배관·가스·전력·냉각·설비실

기사 내용과 무관하게 사람만 세워 놓는 이미지는 금지한다.

### 2-5. 최근 3개 이미지 비교 Gate
새 이미지를 저장하기 전에 최근 3개 대표이미지와 비교한다.
다음 5개 항목 중 **3개 이상이 동일·유사하면 재생성**한다.
1. 인원 수
2. 복장
3. 카메라 구도
4. 배경 공간
5. 핵심 시각 대상

특히 최근 3개가 모두 클린룸 인물사진 계열이면 다음 이미지는 우선적으로 **사람 없는 장비·웨이퍼·로봇·Utility·부품·관제실** 중 하나를 사용한다.

## 3. 대표이미지 파일 버전 규칙 — 덮어쓰기 금지
동일 URL의 브라우저·NAS·CDN 캐시 때문에 수정한 이미지가 구버전으로 보이는 문제를 원천 차단한다.

1. 기사 TXT 파일명은 고정한다.
   - `YYMMDD.AutoGen.기사제목.txt`
2. 대표이미지는 반드시 버전 번호를 붙인다.
   - 최초 이미지: `YYMMDD.AutoGen.기사제목.v1.jpg`
   - 첫 수정: `YYMMDD.AutoGen.기사제목.v2.jpg`
   - 재수정: `YYMMDD.AutoGen.기사제목.v3.jpg`
   - 이후 `v4`, `v5` 순으로 증가한다.
3. **기존 대표이미지와 동일한 파일명으로 덮어쓰지 않는다.** 이미지 내용이 1픽셀이라도 변경되면 새 버전 파일을 만든다.
4. 새 버전 번호는 GitHub에 존재하는 같은 기사 이미지의 최고 `vN`을 확인한 뒤 `N+1`로 정한다.
5. 과거의 무버전 `YYMMDD.AutoGen.기사제목.jpg`는 레거시 `v0`로 취급하며 삭제하지 않아도 된다.
6. `v0` 파일을 새로 생성하지 않는다. 신규 이미지는 반드시 `v1`부터 시작한다.
7. TXT의 논리 stem은 `YYMMDD.AutoGen.기사제목`이며, 이미지의 `.vN`을 제거한 논리 stem이 TXT와 일치해야 한다.
8. 기사 TXT 자체를 수정하는 경우에도 대표이미지를 수정하지 않았다면 이미지 버전은 올리지 않는다. 이미지를 다시 만들거나 편집한 경우에만 새 버전을 만든다.

## 4. 실제 JPG 바이너리 저장 원칙
1. 최종 파일은 반드시 `YYMMDD.AutoGen.기사제목.vN.jpg`라는 **실제 JPEG 바이너리 파일**로 `wskimgit/k-article/main`에 저장한다.
2. `.jpg.b64`, `.b64`, `.txt` 등의 우회 파일을 대표이미지로 저장해서는 안 된다.
3. Base64 문자열 자체, `placeholder`, data URI, 빈 파일, 임시 청크 파일을 최종 이미지로 간주하지 않는다.
4. Base64는 GitHub API로 JPEG 바이너리를 전달하기 위한 **전송 인코딩**으로만 사용할 수 있으며, 최종 저장 경로의 확장자는 반드시 `.jpg`여야 한다.
5. 업로드 과정에서 임시 `.b64` 또는 청크 파일을 만들었다면 최종 JPG 저장 확인 후 즉시 제거한다.
6. TXT와 JPG의 물리 stem이 완전히 같을 필요는 없다. 대신 JPG에서 `.vN`을 제거한 **논리 stem**이 TXT의 stem과 완전히 같아야 한다.
7. 같은 버전 번호의 파일을 재사용하거나 덮어쓰지 않는다.

## 5. GitHub 저장 후 필수 검증
이미지를 로컬에서 생성한 것만으로는 저장 완료가 아니다. 반드시 GitHub 원격 저장소를 다시 조회해 다음을 확인한다.

1. 정확한 `.vN.jpg` 경로가 `k-article/main`에 실제 존재하는가.
2. GitHub에서 해당 파일을 Base64로 다시 읽었을 때 JPEG가 정상적으로 반환되는가.
3. JPEG 시작 시그니처가 `FF D8`이며, 가능하면 종료 시그니처 `FF D9`와 정상 decode까지 확인하는가.
4. 게시용 크기가 1200×675인지 확인하는가.
5. 파일 크기가 0바이트 또는 비정상적으로 작은 placeholder 수준이 아닌가.
6. 새 저장 후 blob SHA가 확인되는가.
7. 같은 기사에 더 높은 `vN`이 이미 존재하지 않는가. 존재하면 그보다 높은 번호로 다시 저장한다.
8. 같은 작업에서 `.jpg.b64` 또는 기타 우회 파일이 남아 있지 않은가. 남아 있으면 삭제한다.
9. GitHub 재조회가 404이거나 실제 JPEG 검증에 실패하면 **이미지 저장 실패**로 판정하고 재시도한다.
10. 이전 버전과 새 버전의 blob SHA가 다름을 확인한다.

## 6. egtech.php 대표이미지 선택 규칙
1. `egtech.php`는 기사 TXT의 논리 stem을 기준으로 이미지 후보를 찾는다.
2. `...v1.jpg`, `...v2.jpg`, `...v3.jpg`가 함께 있으면 **가장 높은 버전 번호를 자동 선택**한다.
3. 버전 파일이 하나라도 있으면 무버전 레거시 이미지는 표시 후보에서 뒤로 밀린다.
4. 버전 파일이 없을 때만 과거 무버전 `.jpg/.jpeg/.png/.webp/.gif`를 `v0` fallback으로 사용한다.
5. 같은 버전에서 확장자가 여러 개면 `jpg → jpeg → png → webp → gif` 순으로 우선한다.
6. 표시 URL에는 필요하면 `mtime-size` 기반 query를 추가해 잔여 브라우저 캐시까지 방지한다.
7. GitHub→NAS 동기화는 새 `vN` 파일을 신규 파일로 내려받고 과거 버전을 자동 삭제하지 않는다.

## 7. 완료 판정 금지 조건
다음 중 하나라도 해당하면 `이미지 저장 완료`, `ERRC PASS`, `기사 생성 완료`라고 보고해서는 안 된다.

- 이미지가 작업공간에만 존재하고 GitHub에는 없는 경우
- GitHub에 `.jpg.b64`만 존재하는 경우
- 파일 내용이 `placeholder` 또는 Base64 텍스트인 경우
- `.vN.jpg` 경로 조회가 404인 경우
- JPEG decode 또는 시그니처 검증에 실패한 경우
- 이미지 수정 후 기존 파일명을 덮어쓴 경우
- 새 이미지의 버전 번호가 기존 최고 버전보다 높지 않은 경우
- TXT 논리 stem과 JPG에서 `.vN`을 제거한 논리 stem이 다른 경우
- 최근 3개 이미지와 비교했을 때 차별화 Gate를 통과하지 못한 경우

TXT만 정상 저장된 경우에는 반드시 `기사 저장 성공 / 이미지 저장 실패`로 구분해서 보고한다.

## 8. 최종 저장 절차
`최근 3개 이미지 확인 → 기사 핵심 장면 선정 → 인원·복장·구도 차별화 → 고품질 이미지 생성 → 육안 품질검사 → 차별화 Gate → 1200×675 JPEG 정규화 → GitHub 동일 기사 최고 이미지 버전 조회 → N+1 결정 → ...vN.jpg 신규 저장(덮어쓰기 금지) → GitHub 원격 재조회 → SHA·시그니처·크기 확인 → 논리 stem 확인 → 우회 .b64 파일 부재 확인 → egtech.php 최신 버전 선택 확인 → 완료 보고`

이 규칙은 이후 모든 K-BIZPOST egTEC AutoGen 대표이미지에 필수 적용한다.
