# K-ARTICLE 대표이미지 생성·저장 규칙 v2.3 — FROZEN

기준일: 2026-09-12
상태: FROZEN / K-ARTICLE-RULES에 대한 필수 이미지 규칙

## 1. 목적
대표이미지는 기사의 기술 내용을 모두 설명하는 도식이 아니라, **기사 주제와 직접 관련된 실제 산업현장을 빠르고 자연스럽게 보여주는 대표사진**을 목표로 한다.

이미지 품질은 유지하되, 무한 재생성·과도한 차별화 검사·복잡한 GitHub 우회 저장으로 작업이 끝나지 않는 문제를 방지한다.

핵심 원칙:
**좋은 이미지 1장 생성 → 필요 시 1회만 재생성 → 직접 GitHub 저장 → 1회 검증 → 종료**

## 2. 이미지 제작 기준
1. 고품질 생성형 이미지 모델을 사용한다.
2. 기본 형식은 사실적인 산업현장 사진형 이미지로 한다.
3. 기사 핵심 주제와 관련된 장면 하나만 표현한다.
4. 기술 내부 구조를 도식적으로 모두 설명할 필요는 없다. 기사 주제와 실제 적용 환경이 자연스럽게 연결되면 충분하다.
5. 16:9 비율을 기본으로 하고 최종 게시용 JPG는 1200×675로 정규화한다.
6. 기사 제목, 통계, 차트, 표, 화살표, 설명 패널, 뉴스페이지·포스터·인포그래픽 형식은 넣지 않는다.
7. 실제 기업 로고·브랜드명·제품명·읽을 수 있는 UI 문구를 넣지 않는다.
8. 우측 하단에는 필요한 경우 `생성형 AI 제작 이미지` 문구만 작게 표시한다.
9. 인터넷 기사 사진을 무단 복제하지 않는다.

## 3. 기사와 이미지의 관련성 판정
다음 조건이면 기사 대표이미지로 인정한다.
- 기사에서 다루는 FAB·Subfab·클린룸·장비·Utility·정비·검사·물류·관제·연구환경 중 하나가 직접 보인다.
- 기사의 핵심 기술이 사용될 법한 실제 산업환경이 자연스럽게 표현된다.
- 독자가 기사와 전혀 무관한 일반 사진으로 오해하지 않는다.

다음은 재생성 사유가 아니다.
- 촉매·센서·AI 알고리즘 등 내부 기술이 사진에서 직접 보이지 않는 경우
- 최근 기사와 산업 조명이나 금속설비 분위기가 일부 유사한 경우
- 인원 수나 카메라 각도가 이전 이미지와 일부 겹치는 경우
- 기술을 설명하는 화살표나 텍스트가 없어서 세부 원리가 즉시 드러나지 않는 경우

## 4. 이미지 차별화 — 권고 규칙
최근 기사와 같은 대표사진을 반복적으로 재사용하지 않는다.
가능하면 사람 수, 복장, 구도, 배경, 핵심 대상 중 2개 이상을 이전 이미지와 다르게 한다.

그러나 차별화는 **재생성 무한루프를 만드는 강제 Gate가 아니다.**
기사와 직접 관련되고 품질이 정상이라면 저장을 우선한다.

주제별 예:
- 예지보전 → 센서·장비 상태진단
- 공정제어 → 장비·제어환경
- 공급망 → Qualification·테스트·장비
- MRO → 부품·물류·정비
- Robotics → 로봇암·자동이송
- Utility → 배관·덕트·가스·냉각·설비실
- 검사 → 계측·X-ray·현미경·검사장비
- 인력 → 교육·정비·기술전수

## 5. 재생성 횟수 제한
### 기본
- 1차 이미지 생성 후 즉시 품질을 판정한다.
- 명백한 문제가 있을 때만 **1회 추가 재생성**한다.
- 한 기사에서 이미지 생성은 **최대 2회**로 제한한다.

### 재생성해야 하는 명백한 문제
- 기사와 전혀 무관한 장면
- 인포그래픽·포스터·뉴스페이지로 생성됨
- 큰 글자·화살표·차트·기업 로고가 들어감
- 사람의 손·얼굴·보호복 또는 장비 구조가 심하게 왜곡됨
- 이미지 자체가 생성되지 않거나 사용할 수 없음

### 2회 모두 실패한 경우
추가 생성하지 않는다.
TXT는 정상 저장하고 다음과 같이 종료한다.
`기사 저장 성공 / 이미지 생성 실패`

## 6. 생성과 저장을 분리한다
이미지가 한 번 정상 생성되면 **저장 오류 때문에 이미지를 다시 생성하지 않는다.**

저장 또는 GitHub 검증이 실패하면 동일한 정상 이미지 바이너리를 다시 사용한다.
이미지를 다시 그리는 것은 원본 이미지 자체가 부적합한 경우에만 한다.

## 7. 파일 버전 규칙
대표이미지는 기존 파일을 덮어쓰지 않는다.

- 최초: `YYMMDD.AutoGen.기사제목.v1.jpg`
- 수정: `...v2.jpg`
- 재수정: `...v3.jpg`

저장 전 GitHub에 존재하는 동일 기사 최고 `vN`을 확인하여 항상 `N+1`로 저장한다.
과거 무버전 이미지는 레거시 `v0`로 취급한다.
TXT 논리 stem과 JPG에서 `.vN`을 제거한 논리 stem은 같아야 한다.

## 8. GitHub 저장 — 직접 경로만 사용
최종 저장소:
- repository: `wskimgit/k-article`
- branch: `main`
- 위치: repository root

대표이미지는 실제 JPEG 바이너리로 직접 저장한다.

권장 절차:
1. 최종 JPG를 1200×675로 정규화
2. GitHub 최고 버전 확인
3. `N+1` 결정
4. JPEG를 Base64 전송 인코딩
5. `create_blob(base64)`
6. 현재 main tree를 기준으로 `create_tree`
7. `create_commit`
8. `update_ref(main)`
9. 최종 `.vN.jpg`를 `fetch_file(..., base64)`로 재조회

**금지:**
- `.jpg.b64`를 최종 이미지로 저장
- Base64 조각 파일을 repository에 남김
- 임시 upload 폴더 생성
- 이미지 한 장 저장을 위해 GitHub Actions workflow 생성
- trigger 파일 생성
- placeholder 저장
- 저장 실패 때문에 새 이미지를 재생성

직접 저장이 1회 실패하면 동일 바이너리로 **1회만 재시도**한다.
두 번째 저장도 실패하면 종료하고 `이미지 저장 실패`로 보고한다.

## 9. 저장 후 검증
GitHub 저장 완료는 다음 최소 조건만 확인한다.
1. 정확한 `.vN.jpg` 경로 존재
2. Base64 재조회 성공
3. JPEG 시작 시그니처 `FF D8`
4. 가능하면 종료 시그니처 `FF D9` 또는 decode 정상
5. 1200×675
6. blob SHA 확인
7. TXT와 이미지 논리 stem 일치
8. `.jpg.b64`, 임시 청크, placeholder가 최종 산출물로 남지 않음

검증은 **1회 수행**한다.
검증 실패 시 저장 자체만 1회 재시도하며, 이미지는 다시 생성하지 않는다.

## 10. egtech.php 표시 규칙
1. 기사 TXT 논리 stem과 같은 이미지 후보를 찾는다.
2. `vN` 중 가장 높은 버전을 표시한다.
3. 버전 파일이 없을 때만 무버전 레거시 이미지를 `v0` fallback으로 사용한다.
4. 같은 버전에서는 `jpg → jpeg → png → webp → gif` 순으로 우선한다.
5. 필요 시 `mtime-size` query로 브라우저 캐시를 방지한다.

## 11. 완료 판정
### 이미지 포함 완료
- 기사 TXT 저장 성공
- 이미지 생성 성공
- 새 `vN.jpg` GitHub 저장 성공
- 원격 재조회 검증 성공

이 경우에만 `ERRC PASS`와 `기사 생성 완료`를 보고한다.

### 부분 완료
TXT만 성공하고 이미지 생성 또는 저장이 실패하면:
`기사 저장 성공 / 이미지 생성 또는 저장 실패`

추가 재생성·추가 우회 저장을 계속하지 않는다.

## 12. 최종 운영 절차
`기사 확정 → 이미지 1차 생성 → 명백한 오류 확인 → 필요 시 1회만 재생성 → 정상 이미지 확정 → 1200×675 JPG 정규화 → GitHub 최고 vN 확인 → N+1 직접 바이너리 저장 → 원격 재조회 1회 → 성공/실패 보고 → 종료`

## 13. 핵심 운영 원칙
- **생성 최대 2회**
- **저장 재시도 최대 1회**
- 저장 실패 시 재생성 금지
- 차별화는 품질 향상용 권고사항이며 무한 재생성 Gate가 아님
- 대표사진은 기술 원리의 완전한 도식이 아니라 기사 주제와 연결된 실제 산업현장이면 충분
- GitHub Actions·trigger·Base64 청크 방식은 대표이미지 저장에 사용하지 않음
- 정상 이미지가 확보되면 빠르게 저장하고 종료
