게시일과 실제 사건·발표일을 반드시 구분한다. 오래된 사건을 최근 기사에서 재언급했다는 이유로 최신 변화처럼 쓰지 않는다.

## 4. 조사 유한 실행
조사는 반드시 끝나야 한다.

1. 기존 `k-article` 기사 제목·핵심 주제를 1회 확인
2. 1차 조사 수행
3. 후보가 없을 때만 조사 범위 1회 확장
4. 그래도 적합 주제가 없으면 `신규 기사 보류(HOLD)`로 종료

동일 검색어 반복, 무기한 자료 탐색, 주제가 나올 때까지 계속 검색하는 행위를 금지한다.

## 6. Evidence Gate
- §6.1을 통과한 자료만 사실 검증에 사용한다. 저작권 검증과 사실 검증은 둘 다 통과해야 한다.
- 특정 기업·제품·기술의 핵심 주장은 재사용 근거가 확인된 1차 자료를 우선 확보한다.
- 교차 확인도 재사용 근거가 확인된 독립 자료로만 수행한다. 조건을 충족하는 교차 자료가 없으면 단일 출처임을 명시하고 검증되지 않은 주장을 확대하지 않는다.
- 기업 발표 하나만 있으면 `회사 발표에 따르면`처럼 출처 성격을 명시한다.
- 수치·성능·비율·금액·일정은 기준 시점을 확인한다.
- 전망·추정은 사실처럼 단정하지 않는다.
- 확인되지 않은 제품명·회사관계·성과를 만들지 않는다.

근거가 약하면 문장을 약화하거나 제거한다.

## 6.1. Copyright Gate — 재사용 근거가 확인된 자료만 선택
**초안에 사실을 반영하거나 이미지 참조자료를 투입하기 전에 검증한다. 재사용 근거가 확인된 자료만 선택하고, 최종 게시 직전에 조건 준수와 실제 제외 여부를 다시 확인한다.**

### A. 선택 가능한 자료와 확인 근거
다음 중 하나의 근거가 원문·권리정책·라이선스 또는 실제 허락 기록에서 확인되고, 이번 이용 목적·방식에 적용되는 자료만 후보로 선택한다.
- 권리자 또는 정당한 허락 권한이 있는 제공자의 명시적 재사용 허락
- 이번 상업적 게시, 필요한 재작성·변형·재배포를 허용하는 공개 라이선스
- 적용 범위와 조건이 명시된 공공·공개 데이터 또는 공공저작물 재사용 정책
- 해당 자료의 퍼블릭 도메인 또는 CC0 등 권리 상태가 확인되는 근거
- 직접 생산·보유한 원자료로서 권리와 제3자 자료 포함 여부를 확인할 수 있는 기록

권리자가 누구인지, 이용조건이 어느 자료에 적용되는지 확인한다. 사이트의 일반 허락이 제3자 사진·도표·인용문에 자동 적용된다고 보지 않는다. 권한 없는 재게시자의 허락이나 불법 유출·복제 자료는 인정하지 않는다.

공식자료·보도자료·논문·통계·기사·보고서·표·차트·사진·그림·캡처·영상·생성 참조자료를 모두 동일하게 검증한다. 오픈액세스, 인터넷 공개, 무료 제공, 출처 표시, AI 사용, 짧은 분량, 낮은 유사도 수치만으로 재사용 근거를 대신하지 않는다.

**'사실만 추출한다', '번역하지 않는다', '문장을 바꿔 쓴다'는 이유만으로 재사용 근거 없는 자료를 PASS시키지 않는다. 이 지시문에서는 그러한 자료를 기사 근거로 선택하지 않는다.**

### B. 실제 이용조건 확인
- 허락·라이선스의 원문 URL 또는 확인 가능한 허락 기록, 명칭·버전, 적용 대상, 확인일을 기록한다.
- 이번 상업적 게시와 필요한 변경·번역·재배포의 허용 범위를 확인한다. 출처·저자·라이선스 표시, 변경 고지, 동일조건 등 요구사항을 실제로 충족한다.
- 비상업적 이용만 허용하는 자료를 상업적 게시에 사용하지 않는다. 변경 금지 조건과 충돌하는 번역·각색·이미지 변형은 하지 않는다. 조건 준수가 불가능하거나 해석이 불분명하면 제외한다.
- 데이터의 개별 수치뿐 아니라 표·도표의 표현, 데이터 묶음의 이용조건, 포함된 제3자 자료까지 확인한다. 표를 새로 그렸다는 이유로 확인을 생략하지 않는다.
- 유료벽·로그인·복제 방지 등 접근 제한을 우회하지 않는다. 검색 도구의 접근 가능성을 재사용 허락으로 해석하지 않는다.
- 재사용 근거와 허락 내용을 LLM이 추정하거나 만들어내지 않는다. LLM이 원문·이용조건을 직접 확인할 수 없으면 PASS하지 않는다.

### C. 판정과 의무적 제외
- **PASS:** A의 재사용 근거와 B의 실제 이용조건 준수를 모두 확인하고 기록했다.
- **HOLD:** 근거나 적용 범위·조건 준수를 확인하지 못했다. 확인 전에는 선정·입력·작성·게시 단계에서 사용하지 않는다.
- **EXCLUDE:** 침해 사실이 확인됐거나 침해 우려, 권한 없는 제공, 이용조건 위반이 있다. 해당 자료 전체를 이번 기사 근거에서 제외한다.

HOLD/EXCLUDE 자료의 문장·구성·표·이미지와 이를 무단 번역·각색한 내용도 제거한다. 해당 자료에서만 가져온 수치·주장·해석은 허용된 별도 원자료에서 다시 검증하지 못하면 삭제한다. 출처 목록에서도 제거하고 제외 사유만 내부 검증표에 남긴다. 외부 기사를 읽은 뒤 출처만 허용 자료로 바꿔 끼워 넣지 않는다.

검증된 대체자료가 있으면 그 자료에서 작성 과정을 다시 시작한다. 남은 자료로 기사 핵심 근거가 충분하지 않으면 **HOLD로 종료하고 게시하지 않는다.** 기사 자체가 PASS이고 이미지만 실패하면 이미지를 게시하지 않고 **기사만 저장 / PARTIAL**로 종료할 수 있다. 기존 조사 확장·수정·생성 횟수를 늘리거나 무기한 허락을 찾지 않는다.

### D. 허용 자료에 기초한 독자적 작성
1. PASS 자료에서 필요한 사실·수치·일정만 선별해 사실 메모를 만든다. 각 항목을 원자료와 연결한다.
2. 사실 메모를 바탕으로 기사 핵심 소식, 제목, 리드, 문단 순서와 설명을 새로 설계한다. 원문을 문장별로 바꿔 쓰거나 번역·축약·동의어 치환하지 않는다.
3. 타사의 제목·특징적인 표현·문단 배열·논지 전개를 재현하지 않는다. 허용 자료라도 그 원문의 기사 구성이나 해석을 그대로 기사화하지 않는다.
4. 원문의 긴 인용, 표·도표·사진·캡처 복제는 기본적으로 사용하지 않는다. 꼭 필요한 원문 인용이 있으면 이번 이용을 허용하는 근거와 조건을 별도로 확인하고 최소 범위만 명확히 구분하여 표시한다.
5. 사업 및 투자 해석은 검증한 사실에서 직접 도출한 독자적 해석으로 작성한다. 타 언론·증권사·블로그의 투자 논리, 추천, 목표주가, 가치평가·전망을 가져와 재포장하지 않는다.
6. 해석의 근거와 성립 조건을 기사 문장 안에서 설명하고, 사실·회사 전망·작성자의 해석을 구분한다. 확인하지 않은 업계 의견, 인터뷰, 전문가 발언, 수익률·목표가·계약·수주를 만들지 않는다. 해석이 뒷받침되지 않으면 생략한다.
7. 투자 시사점은 해당 FAB 기술 변화와 연결되는 설비투자·운영비·고객 도입·서비스 수요 등 범위에서 필요한 경우만 다룬다. 단순 증시 시황·종목 추천으로 조사 범위를 확대하지 않는다.

### E. 검증 기록과 게시 조건
- 검증표: `chatgpt/copyright-checks/YYMMDD.<식별자>.json`. 기사 stem과 연결하고 제목·본문·대표이미지 및 생성 참조자료를 모두 포함한다.
- 최소 항목: `article_stem`, `checked_at`, `sources[]`, `facts[]`, `independent_writing_check`, `article_style_status`, `article_copyright_status`, `image_copyright_status`, `excluded_items[]`, `publication_decision`.
- sources에는 자료명·기관/저자·권리자, 원문 URL·게시일·확인일, 실제 이용 방식, 재사용 근거 유형·근거 URL/허락 기록, 라이선스·적용 범위·조건 준수, PASS/HOLD/EXCLUDE 및 사유를 기록한다.
- facts에는 기사 핵심 사실과 PASS source의 연결을, independent_writing_check에는 문장·구성·사업 및 투자 해석의 독자 작성 여부를 기록한다. 검증표에 원문 전문이나 무단 사진·캡처를 복제하지 않는다.
- 최종 기사에 남은 모든 사실 근거가 PASS인지, HOLD/EXCLUDE 자료 및 파생 내용이 실제 제거됐는지 확인한다. 일반 기사체 여부는 §8과 함께 확인한다.
- 검증표를 결과물과 함께 저장하고 정상 저장 여부를 확인한다. 기록 또는 조건 충족이 확인되지 않으면 COMPLETE를 보고하지 않는다.
- 최종 사용 자료·내용이 바뀌면 ERRC의 수정 1회·재검증 1회 범위에서 해당 항목을 다시 검증한다.
- 실제 확인 없이 '저작권 문제 없음', '완전한 무침해 보장'이라고 단정하지 않는다. 기록에는 확인한 재사용 근거, 준수 조건과 판정을 정확히 적는다.

## 7. 중복 방지
기존 기사 제목뿐 아니라 핵심 기술·기업·적용사례까지 확인한다.

같은 기술이라도 다음이 있으면 후속기사 허용:
- 새 제품·서비스
- 새 고객·적용사례

후속기사라면 무엇이 새로 달라졌는지 본문에서 분명히 드러나야 한다.

## 8. 기사 작성 — 일반적인 뉴스 기사체
분량: 한글 약 1,300~1,700자. 출처·AI 고지·내부 검증 기록은 본문 분량과 구분한다.

### 구성
- 제목은 이번에 확인된 새 소식을 구체적으로 전달한다. 선정적 문구·과장·질문형 보고서 제목을 피한다.
- 첫 문단(리드)에서 누가, 언제, 무엇을 발표·도입·변경했는지와 핵심 의미를 전달한다. 확인되지 않은 육하원칙 요소를 채워 넣지 않는다.
- 이어서 중요한 사실과 기술적 차이, 필요한 배경, FAB 운영·사업에 미치는 영향을 중요도 순으로 자연스럽게 연결한다.
- 투자 시사점이 필요하면 독자적 해석과 그 조건을 본문 문단에 녹인다. 별도 종목 추천표나 투자전략 보고서로 전환하지 않는다.
- 끝 문단은 확인할 후속 일정이나 남은 도입 조건을 구체적으로 짚는다. 막연한 전망·비장한 결론을 반복하지 않는다.
- 매번 같은 항목을 기계적으로 채우지 않는다. 한 기사에 한 가지 핵심 소식을 중심으로 완성한다.

### 문체
- 본문은 완결된 문장과 자연스러운 문단으로 작성하고, 객관적인 기사 문체인 '~했다', '~밝혔다', '~이다'를 사용한다.
- 사실은 출처의 확인 범위에 맞춰 전달한다. 기업 발표 하나가 근거이면 '회사는 …라고 밝혔다'처럼 성격을 밝힌다.
- 기술 용어는 처음 등장할 때 독자가 이해할 수 있도록 짧게 풀어 설명한다. 홍보문·AI 만능론·과장된 효능을 쓰지 않는다.
- 본문에 '문제/변화', '핵심 분석', '평가', '시사점', '투자 전략', '결론' 같은 분석서형 소제목과 번호·불릿·점수표·체크리스트·표를 나열하지 않는다.
- '다음은 적용 검토다', '본 분석에서는', '확인이 필요하다'만 반복하는 미완성 보고서 문장을 쓰지 않는다. 확인 가능한 사실을 우선 제시하고 불확실한 부분은 근거와 함께 간결하게 한정한다.
- Copyright Gate, PASS/HOLD, ERRC, 라이선스 심사 과정, 파일 경로 등 내부 운영 용어는 기사 본문에 넣지 않는다. 출처·필수 라이선스 표시와 AI 고지는 본문 아래 별도 표기하고 검증 과정은 내부 기록에 둔다.

## 11. 이미지 저장 — DIRECT ONE-SHOT 원칙
최종 이미지 한 장이 정상 확보되고 저작권 검증을 통과하면 더 이상의 이미지 조사·품질시험·GitHub 사전검사를 중단한다.

저장 흐름은 다음 한 줄로 고정한다.

`최종 JPG 확정 → 최고 vN/SHA 1회 확인 → 동일 SHA면 기존 이미지 재사용 → 다르면 create_blob → create_tree → create_commit → update_ref → fetch_file 1회 → 종료`

정상 이미지 저장 경로에서 GitHub 관련 호출은 이미지 규칙 v2.8의 **7-call 상한**을 따른다. 저작권 검증표는 TXT와 함께 저장하거나 동일 커밋에 포함하여, 이미지 저장 호출을 반복하지 않는다.

같은 HEAD·tree·파일을 반복 조회하지 않는다.
이미 확보한 정보를 다시 검색하지 않는다.
도구 discovery는 실제 필요한 도구가 없는 경우에만 최대 1회 허용한다.

## 12. GitHub 저장소
- repository: `wskimgit/k-article`
- branch: `main`
- TXT/JPG: repository root

TXT는 UTF-8로 저장한다. 동일 내용이면 불필요한 update commit을 만들지 않는다.

JPG는 실제 JPEG 바이너리만 저장한다.

금지:
- 새 GitHub Actions workflow
- trigger 파일
- `.jpg.b64`
- Base64 chunk
- `_upload_*` 임시 폴더
- placeholder
- `main` force update
- base tree 없는 create_tree

과거 repository에 남은 레거시 workflow/trigger/chunk는 새 작업에서 사용하지 않는다.

## 13. 저장 실패 처리
정상 이미지가 확보된 후 저장 실패가 발생해도 이미지를 다시 만들지 않는다.

허용되는 저장 재시도는 **동시 변경에 따른 non-fast-forward 충돌 1회**뿐이다.
이 경우 같은 blob을 재사용하여 최신 HEAD/base tree에 다시 연결한다.

두 번째 저장도 실패하면 즉시:
`기사 저장 성공 / 이미지 저장 실패 / PARTIAL`
로 종료한다.

우회 저장을 시작하지 않는다.

## 14. ERRC — 1회만
최종 기사·이미지·경로와 §6.1의 검증표를 한 번 검증한다. 모든 사용 자료의 재사용 근거·조건 준수, 핵심 사실과 PASS 자료의 연결, 문장·구성·사업 및 투자 해석의 독자성, §8의 일반 기사체, 기사 PASS와 게시할 이미지 PASS, 제외 자료·파생 내용의 실제 제거, 출처·AI 고지 및 기록 저장을 필수 확인한다. 하나라도 확인되지 않으면 COMPLETE 또는 ERRC PASS로 판정하지 않는다.

실패 시:
- 수정 1회
- 재검증 1회

그 이후 추가 수정·추가 검증을 반복하지 않는다.

## 15. 작업 상태
### COMPLETE
기사 TXT·대표이미지·검증표가 정상 저장되고 모든 사용 자료의 재사용 근거, 기사·이미지 Copyright Gate PASS, 독자적 문장·구성·해석과 일반 기사체 및 최소 검증을 모두 통과.

### PARTIAL
기사의 Copyright Gate PASS 및 검증표 저장은 완료했으나 이미지 생성·저작권 검증·저장 중 하나가 실패하여, 해당 이미지의 게시를 제외한 상태.

### HOLD
적합한 신규 주제가 없거나, 저작권 검증에서 제외한 자료를 빼면 기사 핵심 근거가 부족하여 생성·게시를 보류.

### ERROR
기사/저장 구조 자체를 정상 처리할 수 없는 치명적 오류.

모든 작업은 반드시 네 상태 중 하나로 끝난다.

## 16. HARD STOP
다음 조건 중 하나가 발생하면 추가 시도 없이 즉시 종료한다.

- 조사 확장 1회 소진
- 이미지 생성 2회 소진
- 이미지 저장 재시도 1회 소진
- 동일 SHA 확인(저작권 검증 PASS가 선행되어야 재사용·COMPLETE 허용)
- GitHub 원격 재조회 성공
- ERRC 재검증 1회 소진

**성공 후 추가 확인을 하지 않는다. 실패 후 새로운 우회 경로를 찾지 않는다.**
