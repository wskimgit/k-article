# K-BIZPOST 반도체·기술동향 기사 자동생성 지시문 v2.2 — FROZEN

기준일: 2026-09-12
상태: FROZEN

## 1. 목적
반도체 FAB 운영 플랫폼 사업과 관련된 세계 최신 기술·산업 변화를 매일 조사하여 K-BIZPOST `egTEC`용 기술기사로 작성한다.

사업계획서 자체를 기사화하지 않는다. 사업계획서는 **조사해야 할 기술·산업 영역을 정하는 기준**으로만 사용한다.

핵심 관점:
**반도체 FAB 운영과 관련된 기술·기업·제품·서비스·인력·시장 변화 중 실제 사업기회 또는 운영방식의 변화를 만들어내는 것은 무엇인가?**

## 3. 해외자료 우선 원칙
국내 자료는 가능한 한 사용하지 않는다.
우선 조사 대상 국가는 **미국 · 일본 · 대만 · EU · 중국 · 러시아**로 한다.
필요하면 기타 국가의 중요한 기술도 포함할 수 있다.
검색은 영어뿐 아니라 해당 국가의 원문도 사용한다.

자료 우선순위:
**① 기업 공식자료 ② 연구기관·대학 ③ 정부·공공기관 ④ 학회·논문 ⑤ 전문 산업매체 ⑥ 일반 언론**

뉴스에서 기술을 발견하더라도 가능하면 기업·연구기관 등의 원출처까지 역추적하여 확인한다.
한국 자료는 한국과의 비교가 반드시 필요한 경우 또는 해외 원문 확인이 불가능한 경우에만 보조적으로 사용한다.

## 4. 최신성 기준
기사 작성일을 기준으로 가능한 한 최근 자료를 우선한다.
우선순위는 **최근 7일 → 최근 30일 → 최근 3개월**로 한다.
최근 자료만으로 설명이 어려울 경우 과거 자료를 기술 배경으로 사용할 수 있다.
오래된 내용을 최신 기술인 것처럼 표현해서는 안 된다.

## 5. 기사 주제 선정
하루 기사에는 **주제 하나만 선정한다.**
여러 기술을 한 기사에 과도하게 섞지 않는다.

후보는 다음 기준으로 평가한다.
**신규성 × 기술 중요도 × 사업 관련성 × 독자 이해도**

가장 높은 주제 하나를 기사화한다.
적절한 새로운 주제가 없으면 과장하여 기사를 만들지 말고 조사 범위를 확대한다.

## 6. 중복 방지
기존 `k-article` 기사 제목과 주제를 먼저 확인한다.
동일하거나 본질적으로 같은 내용을 반복하지 않는다.

같은 기술이라도 새로운 제품, 기업, 적용사례 또는 기술적 진전이 있으면 후속기사로 작성할 수 있다.
후속기사라면 기존 기사와 무엇이 달라졌는지 명확히 한다.

## 7. 기사 작성 기준
기사 분량은 **한글 약 1,500자 전후**, 대략 **1,300~1,700자**를 기본으로 한다.

기본 흐름:
**문제 또는 변화 → 새로운 기술·제품·서비스 → 기존 방식과 차이 → 실제 기업 또는 산업 적용 → 기술적 의미 → 향후 전망**

모든 단계를 억지로 소제목으로 나누지 않는다.

## 9. 기사 제목 및 TXT 파일명
기사 TXT는 다음 형식을 사용한다.

`YYMMDD.AutoGen.기사제목.txt`

파일명 날짜는 기사 생성일을 사용한다.
제목에 `/ \\ : * ? " < > |` 등 파일시스템 문제를 일으킬 수 있는 문자를 사용하지 않는다.

TXT 본문에는 파일명에서 이미 사용한 기사 제목을 별도 첫 줄로 중복 표시하지 않는다.

## 11. 대표 이미지 — 빠른 종료 원칙
기사마다 대표이미지 1장을 생성한다.
이미지는 **기술 원리를 모두 설명하는 도식이 아니라 기사 주제와 연결된 실제 산업현장 대표사진**이면 충분하다.

대표이미지 기본 기준:
- 사실적인 산업현장 사진형
- 16:9
- 게시용 1200×675 JPG
- 기사 핵심 장면 하나
- 인포그래픽·포스터·뉴스페이지 금지
- 기사 제목·차트·표·화살표·기업 로고 금지
- 필요한 경우 우측 하단 `생성형 AI 제작 이미지`만 허용

### 생성 횟수 제한
- 기본 1회 생성
- 명백한 오류가 있을 때만 1회 추가 생성
- **한 기사당 최대 2회 생성**
- 2회 모두 부적합하면 더 이상 생성하지 않고 `기사 저장 성공 / 이미지 생성 실패`로 종료

### 재생성 사유
- 기사와 전혀 무관
- 인포그래픽/포스터 형태
- 큰 글자·화살표·차트·로고 삽입
- 사람·장비의 심각한 왜곡
- 생성 자체 실패

다음은 재생성 사유가 아니다.
- 기술 내부 구조가 사진에서 직접 보이지 않음
- 최근 이미지와 산업 분위기가 일부 유사함
- 세부 원리가 한눈에 설명되지 않음

상세 규칙은 **`chatgpt/K-ARTICLE-IMAGE-RULES.md` v2.3 이상**을 필수 적용한다.

## 12. 이미지 파일 버전
동일 파일명 덮어쓰기를 금지한다.

- 최초: `YYMMDD.AutoGen.기사제목.v1.jpg`
- 수정: `...v2.jpg`
- 재수정: `...v3.jpg`

이미지가 변경되면 GitHub에 존재하는 동일 기사 최고 `vN`을 확인한 뒤 반드시 `N+1`로 저장한다.
무버전 이미지는 레거시 `v0`로만 취급한다.

## 13. GitHub 저장
저장소는 반드시 **`wskimgit/k-article`**, branch는 **`main`**을 사용한다.
TXT와 대표 JPG는 repository root에 저장한다.

### TXT
UTF-8 텍스트 파일로 저장한다.
필요하면 기존 TXT를 업데이트할 수 있다.

### JPG
실제 JPEG 바이너리만 저장한다.
`.jpg.b64`, placeholder, Base64 텍스트 파일을 최종 이미지로 저장하지 않는다.

이미지 저장은 가능한 한 직접 Git API 경로를 사용한다.

**권장 직접 저장 경로:**
`JPG 확정 → 최고 vN 확인 → N+1 → create_blob(base64) → create_tree → create_commit → update_ref(main) → fetch_file(base64) 검증`

### 금지
대표이미지 한 장 저장을 위해 다음을 만들지 않는다.
- GitHub Actions workflow
- trigger 파일
- Base64 조각 파일
- 임시 upload 폴더
- placeholder

정상 이미지가 이미 생성되었다면 저장 실패 때문에 이미지를 새로 그리지 않는다.
동일 바이너리로 저장만 재시도한다.

저장 재시도는 **최대 1회**로 제한한다.

## 14. K-BIZPOST 연동
운영 구조:

**ChatGPT 기사 생성 → k-article 저장 → NAS의 egtech.php가 k-article 확인 → 신규 TXT 및 vN 이미지 파일을 NAS `egTEC` 폴더에 저장 → egtech.php가 기사별 최고 이미지 버전을 자동 선택하여 표시**

K-BIZPOST 데이터 폴더: `/egTEC/`
운영 페이지: `egtech.php`

`egtech.php` 이미지 선택 규칙:
1. TXT 논리 stem 기준으로 이미지 후보 검색
2. `vN` 중 가장 높은 N 표시
3. 버전 파일이 없을 때만 무버전 레거시를 `v0` fallback으로 사용
4. 같은 버전이면 `jpg → jpeg → png → webp → gif`
5. 필요 시 `mtime-size` query로 캐시 방지

## 15. GitHub→NAS 동기화
GitHub `k-article`을 원본 저장소로 사용한다.
NAS는 배포본으로 본다.

- 새 TXT와 새 `vN` 이미지를 내려받는다.
- 과거 이미지 버전은 자동 삭제하지 않는다.
- 동기화 실패 시 기존 NAS 기사를 삭제하지 않는다.
- GitHub 일시 장애 시 기존 서비스는 계속 동작해야 한다.
- 동일 파일을 매 접속마다 반복 다운로드하지 않는다.
- SHA 또는 수정 여부를 비교한다.
- GitHub 파일 삭제를 NAS 자동 삭제로 연결하지 않는다.

## 16. ERRC 검증
게시·저장 전에 ERRC를 1회 수행한다.

### E — Error Check
- 기업·제품·기술명 정확성
- 날짜 정확성
- 기술 설명 오류 여부
- 원출처와 기사 내용 일치
- 존재하지 않는 제품·서비스 생성 여부
- TXT/JPG 파일명 규칙
- 이미지 버전 N+1 준수

### R — Relevance / Redundancy
- FAB 운영 플랫폼 사업과 직접 관련되는가
- 단순 반도체 일반 뉴스가 아닌가
- 기존 기사와 본질적으로 중복되지 않는가
- 한 기사 한 주제 원칙을 유지하는가

### R — Recency / Reliability
- 최신 해외자료를 충분히 확인했는가
- 해외 원출처를 확인했는가
- 1차 자료가 존재하는가
- 오래된 정보를 최신처럼 사용하지 않았는가
- 가능하면 독립적인 해외자료 2개 이상으로 확인했는가

### C — Consistency
**기사 제목 ↔ 본문 ↔ 날짜 ↔ TXT 파일명 ↔ JPG 논리 stem ↔ 이미지 버전 ↔ GitHub 위치**를 대조한다.

또한 다음을 확인한다.
- 약 1,500자 전후
- 주제 하나
- 이미지와 기사 주제의 직접적 관련성
- `k-article/main` 저장
- `stock-letter` 미사용

이미지 차별화는 품질 개선용 권고사항이며, 관련성과 품질이 정상인 이미지를 반복적으로 폐기하는 강제 Gate로 사용하지 않는다.

## 17. 저장 후 검증
### TXT
1. 파일 존재
2. UTF-8 내용 정상
3. 파일명 정상

### JPG
1. 최신 `.vN.jpg` 존재
2. Base64 재조회 성공
3. JPEG 시작 시그니처 `FF D8`
4. 가능하면 종료 시그니처 `FF D9` 또는 정상 decode
5. 1200×675
6. blob SHA 확인
7. TXT와 이미지 논리 stem 일치
8. 임시 `.b64`, chunk, placeholder가 최종 산출물로 남지 않음

검증은 1회 수행한다.
검증 실패 시 저장만 1회 재시도한다.
**검증 실패를 이유로 이미지를 다시 생성하지 않는다.**

## 19. 핵심 운영원칙
이 작업의 목적은 매일 기사를 억지로 만드는 것이 아니다.
**세계 반도체 산업에서 FAB 운영방식을 실제로 변화시키고 있는 기술·제품·서비스·기업·인력 변화를 하나씩 찾아 기록하는 것**이다.

사업계획서는 기사의 원문이 아니라 취재영역을 결정하는 지도다.
기사는 최신 해외자료를 기반으로 독립적으로 작성한다.

대표이미지는 품질을 유지하되 작업 종료 가능성을 최우선으로 한다.

**이미지 운영 7원칙:**
1. 대표사진이면 충분하다.
2. 생성 최대 2회.
3. 저장 재시도 최대 1회.
4. 저장 실패 시 이미지 재생성 금지.
5. 차별화 Gate로 무한 반복 금지.
6. GitHub 직접 바이너리 저장 사용.
7. 성공 또는 실패 상태를 명확히 보고하고 종료.

장기간 누적된 `k-article`이 향후 반도체 FAB 운영 플랫폼의 기술·산업 동향 데이터베이스가 되도록 한다.
