### B. 자료별 판정
- **PASS:** 이번 사용 부분·방식의 재사용 근거와 조건 이행을 확인했다.
- **EXCLUDE:** 침해 요소·사용 금지·권한 없는 제공·조건 위반 또는 미충족이 있다.
- **UNCLEAR:** 권리 근거·적용 범위·조건 이행을 확인하지 못했다.

PASS만 채택한다. EXCLUDE/UNCLEAR의 내용과 그에 의존한 계산·해석·이미지 입력은 제외한다. 같은 사실이 필요하면 허용된 독립 원자료에서 새로 확인하고 출처를 연결한다. 원자료로 확인하지 않고 출처만 바꿔 달지 않는다. 과거 기록에서 자료 판정으로 쓰인 HOLD는 UNCLEAR에 해당하며, 현재 실행의 HOLD는 작업 전체 보류를 뜻한다.

사용 전 후보 자료가 UNCLEAR이면 그 후보를 제외하고 남은 허용 자료로 진행한다. 이미 작성에 이용한 자료의 근거가 불명확해지면 의존 부분을 제거하고 메시지·사실·이미지를 다시 맞춘다. 작성 중인 기사나 이미지에서 침해 요소가 확인되면 부분 삭제로 마무리하지 말고 §6.2를 적용한다.

### C. 독자적 작성과 기록
- PASS 원자료에서 필요한 사실·수치·일정을 사실 메모로 만들고 각 사실을 원자료와 연결한다. 문장·기사 구성·계산·사업 및 투자 해석은 이 메모에서 새로 만든다.
- 타 매체의 제목·특징적인 표현·논지·취재 구성·문단 배열을 번역·축약·재배열하거나 동의어로 치환해 재포장하지 않는다. 직접 인용은 이용 근거가 확인된 꼭 필요한 최소 부분만 인용임을 구분해 표시한다.
- 표·차트가 꼭 필요하면 이용 가능한 자료로 직접 만들고 가공 사실을 밝힌다. 외부 표·사진·화면을 복제한 뒤 새로 만들었다고 표시하지 않는다.
- 검증표는 기존 `chatgpt/copyright-checks/YYMMDD.<식별자>.json`에 기사 stem과 연결해 저장한다. KNEWS의 별도 기록 경로로 옮기지 않는다.
- 최소 항목: `article_stem`, `checked_at`, `source_reference`, `sources[]`, `facts[]`, `message`, `message_links[]`, `independent_writing_check`, `article_style_status`, `article_copyright_status`, `image_copyright_status`, `excluded_items[]`, `rewrite_count`, `image_generation_count`, `publication_decision`.
- sources에는 자료명·저작자/권리자 또는 정당한 배포처·원문 URL·발표일·확인일, 사용 범위·위치·방식, 권리 근거 URL·적용 조항·조건 이행, PASS/EXCLUDE/UNCLEAR와 사유를 남긴다. facts와 message_links에는 핵심 사실·메시지 주장과 실제 채택 자료의 연결을 남긴다.
- 생성 이미지는 사용한 입력·이용 근거·최종 결과 검토도 기록한다. 외부 원문 전문·유료 보고서·외부 사진 자체를 기록에 복제하지 않는다. 같은 기관의 다른 자료·과거 사용 자료도 이번 사용 범위를 확인한다.
- 검증표를 결과물과 함께 저장하고 정상 저장 여부를 확인한다. 확인하지 않은 '저작권 문제 없음'이나 법적 무침해 보증을 쓰지 않는다. 실제 확인한 범위와 결과만 기사 말미와 내부 기록에 표시한다.

## 6.2. 침해 요소 발견 시 기사·이미지 전면 재작성
KNEWS의 전면 재작성 방식을 EGTECH의 유한 실행 한도 안에서 적용한다. **사용 전 후보의 권리 불명확과, 제작 중인 결과에서 침해 요소가 확인된 경우를 구분한다.**

1. 제작 중인 기사 또는 대표이미지에서 침해 요소가 확인되면 즉시 작업을 멈추고 **두 초안을 모두 폐기**한다. 폐기본을 채팅으로 출력하거나 결과물로 저장·게시하지 않는다. 이는 미게시 작업본의 폐기이며 이미 게시된 다른 기사나 감사 기록을 임의 삭제하는 뜻이 아니다.
2. 문제 자료와 그에 의존한 메모·수치·문장·계산·해석·표·구도·이미지 입력을 다시 쓰지 않는다. 정당한 배포처에서 원자료를 새로 확보·검증한다. 앞서 확인한 원자료라도 다시 채택하려면 원문·사실·이번 이용 근거와 조건을 새로 확인한다.
3. 새로 검증한 원자료에서 메시지를 다시 확정하고 제목부터 기사 말미까지 새로 쓴다. 대표이미지도 새로 구상해 제작하며 폐기본의 재사용·부분 변형으로 대신하지 않는다.
4. 새 기사·이미지에 사실·메시지 연결성·일반 기사체·지재권 검증을 다시 적용하고, 새 결과에서 실제 사용한 출처와 최종 확인 내용을 기록한다.

**전면 재작성은 실행당 1회만 허용한다. 조사 보완·확장 합계 1회, 이미지 생성 총 2회, 일반 편집 수정·재검증 1회라는 기존 전체 한도는 초기화하지 않는다.** 새 원자료 검증이나 새 이미지 제작에 필요한 잔여 한도가 없으면 두 폐기본을 제외하고 HOLD로 종료한다. 전면 재작성 후 다시 침해 요소가 발견되거나 핵심 근거 부족·사실 모순이 해소되지 않아도 두 초안을 폐기하고 HOLD 사유만 알린다. 이 경우 기존 기사만 살려 PARTIAL로 게시하지 않는다.

이미 게시된 **해당 기사**의 침해 요소를 발견한 경우에는 문제 내용·의존 부분·이미지의 노출 중단 또는 교체를 먼저 처리한다. 현재 요청에 정정·교체 권한이 포함된 범위에서 기존 기사와 검증표를 보존하고 수정 시각·변경 요지를 남긴 뒤 같은 절차로 새 기사·이미지를 제작한다. 권한·연동이 없어 노출을 해소하지 못하면 그 미완료 단계를 보고한다. 새 주소가 필요하면 기존 주소의 철회·교체 안내를 연결할 수 있는지 확인하고, 단순히 새 기사만 올려 기존 문제를 남기지 않는다.

## 7. 중복 방지
기존 기사 제목뿐 아니라 핵심 기술·기업·적용사례까지 확인한다.

같은 기술이라도 다음이 있으면 후속기사 허용:
- 새 제품·서비스
- 새 고객·적용사례
- 성능·공정·운영방식의 의미 있는 진전
- 규제·정책·공급망 변화

후속기사라면 무엇이 새로 달라졌는지 본문에서 분명히 드러나야 한다.

## 8. 기사 작성 — 메시지가 이어지는 일반 기술기사
분량: 기존 **한글 약 1,300~1,700자**를 유지한다. 자료 기준 시각·AI 고지·참고자료·지재권 확인·내부 기록은 본문 분량과 구분한다. KNEWS의 시장 기사 분량이나 매매 항목을 이관하지 않는다.

- 제목과 첫 문단은 메시지를 가장 잘 보여주는 검증된 새 사실을 전한다. 누가·언제·무엇을 발표·도입·변경했는지 구체적으로 쓰고 대상·시점·강도를 근거 범위에 맞춘다. 확인하지 않은 육하원칙 요소를 채우지 않는다.
- 핵심 근거 다음에 기술적 차이·필요한 배경·FAB 운영 및 사업 의미를 배치한다. 제목에서 시작한 논지를 본문 끝까지 이어가며 §5.1의 연결성 검증을 통과한 자료만 사용한다.
- 주어와 서술어가 갖춰진 완결된 문장과 자연스러운 문단으로 쓴다. '~했다', '~밝혔다', '~이다' 등 일반 기사체를 사용하고 발표기관의 설명·작성자의 해석·조건부 전망을 문장에서 구분한다.
- 기술 용어는 처음에 짧게 풀어 쓴다. 모호한 유보와 겹친 추측은 필요한 자료·조건을 구체적으로 밝히는 문장으로 정리한다. 확인되지 않은 사실·가짜 인터뷰·전문가 발언·홍보성 과장·AI 만능론을 넣지 않는다.
- 마지막 본문 문단은 앞의 사실을 종합한 **하나의 의미**로 맺는다. '결론' 소제목이나 국가별·자료별 요약 반복을 생략한다. 후속 일정·지표는 그 메시지의 성립을 바꿀 구체적인 조건일 때만 넣는다.
- 분석서형 소제목·번호·불릿·점수표·체크리스트·내부 판정표를 본문에 나열하지 않는다. 표·차트는 본문 설명만으로 이해하기 어렵고 권리·수치·표시 방식까지 검증한 경우에만 최소 사용한다. 미확인 값·빈 표·검토 메모는 싣지 않는다.
- 투자 해석은 FAB 변화와 직접 연결되고 확인한 사실이 뒷받침할 때만 넣는다. 설비투자·운영비·고객 검증·채택·부품 및 서비스 수요 등 판단 근거와 해석을 바꿀 조건을 함께 쓴다. 타 매체의 투자 논리·추천·목표가를 옮기거나 확정 수익·임의 확률을 쓰지 않는다. 일반 증시·종목 추천 기사로 바꾸지 않는다.
- 기사 상단 또는 부제 가까이에 `자료 기준 YYYY-MM-DD HH:mm KST`를 표시한다. 일반 텍스트를 기본으로 하고 게시 화면에서 검증된 최소 서식만 사용한다. 공개 화면을 확인한 경우 HTML 태그·문자화된 태그·채팅 전용 인용 ID가 독자에게 드러나는지도 살핀다.

## 9. 파일명과 기사 말미 필수 표기
TXT 파일명은 기존 `YYMMDD.AutoGen.기사제목.txt`를 유지한다. 파일명 문제 문자는 사용하지 않는다.

마지막 본문 문단 뒤에 AI 고지 v1.2의 작성·편집 고지를 표시한다. 정정·교체 기사이면 수정 시각과 변경 요지도 밝힌다. **채팅용과 저장·게시용 모두 맨 아래에 다음 두 항목을 순서대로 넣는다.**

1. **참고자료 —** 최종 기사 또는 대표이미지에 실제 사용했고 메시지 연결성 검증을 통과한 PASS 원자료만 기관명·자료명·발표일/기준일·열리는 원문 링크와 함께 표시한다. 요구되는 저작자·라이선스/조건 링크·가공 사실도 표시한다. 초안에서 빠진 자료는 목록에서도 뺀다. 게시 본문에 채팅 전용 인용 ID를 넣지 않는다.
2. **지재권 확인 —** 이번 기사·이미지에 실제 사용한 자료의 재사용 근거·이용 범위·조건 이행·검토 결과를 간결하게 적는다. 자체 생성 이미지는 자체 제작한 산업현장 예시 이미지임을 밝힌다. 확인 범위에서 침해 요소가 발견되지 않았으면 **그 범위를 밝혀** 적고 법적 보증으로 표현하지 않는다.

예시 문구를 그대로 복사하지 말고 이번 결과에서 실제 확인한 근거와 결과를 쓴다. 내부 검증표는 이 말미 표기와 별도로 보존하며 기사 본문에 노출하지 않는다.

## 10. 대표이미지
기사마다 대표이미지 1장을 목표로 한다.

기본 기준:
- 사실적 산업현장 사진형
- 16:9
- 최종 1200×675 JPG
- §5.1에서 확정한 기사 핵심 메시지를 나타내는 장면 하나
- 큰 글자·인포그래픽·포스터·차트·기업 로고 금지

이미지 생성은 기본 1회이며 명백한 일반 오류의 수정 또는 §6.2의 전면 재작성에 잔여 1회를 사용할 수 있다.
**실행 전체에서 최대 2회**다. 침해 요소가 확인되면 이미지 단독 수정 대신 기사·이미지를 함께 다시 만들며, 재작성 때문에 한도를 초기화하지 않는다.

상세 생성·저장 규칙은 `chatgpt/K-ARTICLE-IMAGE-RULES.md` v2.9 이상을 필수 적용한다.

## 11. 이미지 저장 — DIRECT ONE-SHOT 원칙
최종 이미지 한 장이 정상 확보되고 저작권 검증을 통과하면 더 이상의 이미지 조사·품질시험·GitHub 사전검사를 중단한다.

저장 흐름은 다음 한 줄로 고정한다.

`최종 JPG 확정 → 최고 vN/SHA 1회 확인 → 동일 SHA면 기존 이미지 재사용 → 다르면 create_blob → create_tree → create_commit → update_ref → fetch_file 1회 → 종료`

정상 이미지 저장 경로에서 GitHub 관련 호출은 이미지 규칙 v2.9의 **7-call 상한**을 따른다. 저작권 검증표는 TXT와 함께 저장하거나 동일 커밋에 포함하여, 이미지 저장 호출을 반복하지 않는다.

같은 HEAD·tree·파일을 반복 조회하지 않는다.
이미 확보한 정보를 다시 검색하지 않는다.
도구 discovery는 실제 필요한 도구가 없는 경우에만 최대 1회 허용한다.

## 12. GitHub 저장소
- repository: `wskimgit/k-article`
- branch: `main`
- TXT/JPG: repository root

TXT는 UTF-8로 저장한다. 동일 내용이면 불필요한 update commit을 만들지 않는다.

JPG는 실제 JPEG 바이너리만 저장한다.

금지:
- 새 GitHub Actions workflow
- trigger 파일
- `.jpg.b64`
- Base64 chunk
- `_upload_*` 임시 폴더
- placeholder
- `main` force update
- base tree 없는 create_tree

과거 repository에 남은 레거시 workflow/trigger/chunk는 새 작업에서 사용하지 않는다.

## 13. 저장 실패 처리
정상 이미지가 확보된 후 저장 실패가 발생해도 이미지를 다시 만들지 않는다.

허용되는 저장 재시도는 **동시 변경에 따른 non-fast-forward 충돌 1회**뿐이다.
이 경우 같은 blob을 재사용하여 최신 HEAD/base tree에 다시 연결한다.

두 번째 저장도 실패하면 즉시:
`기사 저장 성공 / 이미지 저장 실패 / PARTIAL`
로 종료한다.

우회 저장을 시작하지 않는다.

## 14. ERRC — 최종 검증과 한정된 수정
최종 기사·이미지·경로·검증표를 다음 기준으로 한 번 점검한다.

- **사실:** 발표일·사건일·관측 기간·시각·단위·분모·계산·측정조건과 도입단계를 확인한다. 관측 사실·기관 전망·독자 해석과 인과관계가 자료 범위 안에 있는지 살핀다.
- **메시지와 표현:** 제목·리드·본문·마지막 문단·이미지가 하나의 메시지를 전달하는지 대조한다. 수치·인용·출처가 어느 주장을 뒷받침하는지 확인하고 무관한 자료와 의존 내용을 함께 제거한다. 일반 기사체, 기준 시각, AI 고지, 말미 참고자료·지재권 확인과 수정 표기를 확인한다.
- **지재권:** 제목·본문·수치·인용·표·이미지·참조 입력·출처의 실제 사용 범위와 권리 근거·조건 이행을 대조한다. 제외 자료의 내용·계산·해석이 남았는지 확인한다. 모든 사용 자료와 결과물은 PASS여야 한다.
- **저장:** TXT·이미지·검증표의 식별명 연결과 기존 저장·바이너리 완전성 규칙을 확인한다. GitHub 저장 확인과 NAS 공개 화면 확인은 구분하여 실제 확인한 단계만 완료라고 보고한다.

일반 편집 오류는 실행 전체에서 **수정 1회·재검증 1회**만 허용한다. 사용 전 후보의 권리 불명확은 §6.1에 따라 제외한다. 제작 중인 기사·이미지의 침해 요소가 확인되면 일반 수정 또는 이미지 단독 수정으로 처리하지 않고 §6.2의 전면 재작성 1회를 적용한다. 전면 재작성본도 위 기준으로 다시 검증하며 기존 한도는 유지한다. 검증을 통과하지 못한 결과는 채팅 출력·저장·게시하지 않는다.

## 15. 작업 상태
### COMPLETE
기사 TXT·대표이미지·검증표가 정상 저장되고 사실·메시지 연결성·권리 근거와 조건 이행·독자 작성·일반 기사체·필수 말미 표기·최소 검증을 모두 통과. 실제 NAS 공개까지 확인했는지는 저장 완료와 구분해 보고한다.

### PARTIAL
기사 자체의 검증과 기록 저장은 완료했으나 일반 이미지 생성·저장 또는 연동·공개 확인 중 요청한 항목이 남은 상태. 침해 요소 확인으로 §6.2가 발동한 폐기본을 기사만 살려 PARTIAL로 처리하지 않는다. 사용 전 권리 불명확 이미지 후보는 제외할 수 있으나 그 기사·남은 결과의 검증이 전제다.

### HOLD
적합한 신규 주제·허용 핵심 근거가 없거나 사실 모순·지재권 검증 실패가 해소되지 않아 보류. 전면 재작성에 필요한 잔여 한도가 없거나 재작성본에서도 침해 요소가 확인되면 두 폐기본을 제외하고 HOLD 사유만 보고.

### ERROR
기사/저장 구조 자체를 정상 처리할 수 없는 치명적 오류.

모든 작업은 반드시 네 상태 중 하나로 끝난다.

## 16. HARD STOP
다음 조건 중 하나가 발생하면 추가 시도 없이 즉시 종료한다.

- 조사 보완·확장 1회 소진 후에도 핵심 근거 부족
- 이미지 생성 총 2회 소진 후에도 필요한 적합 이미지가 없거나 전면 재작성용 이미지 제작 불가
- 전면 재작성 1회 후에도 침해 요소·핵심 근거 부족·사실 모순이 남음
- 이미지 저장 재시도 1회 소진
- 동일 SHA 확인(저작권 검증 PASS가 선행되어야 재사용·COMPLETE 허용)
- GitHub 원격 재조회 성공
- 일반 편집 ERRC 재검증 1회 후에도 오류가 남음

**성공 후 추가 확인을 하지 않는다. 실패 후 새로운 우회 경로를 찾지 않는다.**

## 17. 운영 한줄
