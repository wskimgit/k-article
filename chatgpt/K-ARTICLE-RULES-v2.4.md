# K-BIZPOST egTEC 반도체·기술동향 AutoGen 지시문 v2.4 — FROZEN

기준일: 2026-09-12
상태: FROZEN

## 0. 문서 권한과 적용 순서
이 문서는 K-BIZPOST `egTEC` AutoGen 기사 생성·검증·저장 운영의 최신 기준이다.

적용 순서:
1. 기사 Canonical: `chatgpt/K-ARTICLE-RULES.md`
2. Frozen Snapshot: `chatgpt/K-ARTICLE-RULES-v2.4.md`
3. 대표이미지 Canonical: `chatgpt/K-ARTICLE-IMAGE-RULES.md` v2.5 이상
4. AI 고지: `chatgpt/K-ARTICLE-RULES-AI-DISCLOSURE.md`
5. 최신 포인터: `chatgpt/EGTECH-CURRENT.md`

충돌 시 더 구체적인 최신 FROZEN 규칙을 우선한다. 과거 Frozen Snapshot은 수정하지 않는다.

## 1. 목적
세계 최신 반도체 FAB 운영·장비·Utility·유지보수·AI·자동화·MRO·인력·공급망 변화를 조사해 K-BIZPOST `egTEC` 기술기사로 작성한다.

사업계획서 자체를 기사화하지 않고, 조사 범위와 사업관련성 판단 기준으로만 사용한다.

핵심 질문:
**FAB 운영 방식이나 관련 사업기회를 실제로 바꾸는 새로운 변화가 무엇인가?**

- FAB / Subfab / 클린룸 / Utility
- 반도체 생산·연구장비
- 유지보수 / Predictive Maintenance
- FDC / APC / Digital Twin
- MES / EAM / CMMS / Workflow 자동화
- Industrial AI / LLM / RAG / AI Agent
- Robotics / Physical AI
- MRO / 부품·소재·장비 공급망
- 원격진단 / 원격지원
- 전문인력 부족 / 기술전수
- 신규 제품·서비스·기업 사업
- 연구기관·대학 기술
- FAB 운영에 직접 영향을 주는 정책·규제

단순 주가·증시·일반 시황은 제외한다.

## 3. 자료 우선순위와 최신성
우선 조사 지역은 미국·일본·대만·EU·중국·러시아이며 필요 시 기타 국가를 포함한다.

자료 우선순위:
`기업 공식자료 → 연구기관·대학 → 정부·공공기관 → 학회·논문 → 전문 산업매체 → 일반 언론`

최신성 우선순위:
`최근 7일 → 최근 30일 → 최근 3개월`

게시일과 실제 사건·발표일을 반드시 구분한다. 오래된 사건을 최근 기사에서 재언급했다는 이유로 최신 변화처럼 쓰지 않는다.

## 4. 조사 유한 실행
조사는 반드시 끝나야 한다.

1. 기존 `k-article` 기사 제목·핵심 주제를 1회 확인
2. 1차 조사 수행
3. 후보가 없을 때만 조사 범위 1회 확장
4. 그래도 적합 주제가 없으면 `신규 기사 보류(HOLD)`로 종료

동일 검색어 반복, 무기한 자료 탐색, 주제가 나올 때까지 계속 검색하는 행위를 금지한다.

## 5. 주제 Gate
기사당 주제 하나만 선택한다.

필수 조건:
- FAB 운영 또는 관련 사업과 직접 연결
- 기존 기사와 본질적으로 중복되지 않음
- 최신 변화 또는 의미 있는 후속 진전 존재
- 확인 가능한 근거 존재

평가축:
- 신규성
- 기술 중요도
- 사업/운영 관련성
- 근거 신뢰도

## 6. Evidence Gate
- 특정 기업·제품·기술의 핵심 주장은 1차 자료를 우선 확보한다.
- 가능하면 독립 해외자료로 교차 확인한다.
- 기업 발표 하나만 있으면 `회사 발표에 따르면`처럼 출처 성격을 명시한다.
- 수치·성능·비율·금액·일정은 기준 시점을 확인한다.
- 전망·추정은 사실처럼 단정하지 않는다.
- 확인되지 않은 제품명·회사관계·성과를 만들지 않는다.

근거가 약하면 문장을 약화하거나 제거한다.

## 7. 중복 방지
기존 기사 제목뿐 아니라 핵심 기술·기업·적용사례까지 확인한다.

같은 기술이라도 다음이 있으면 후속기사 허용:
- 새 제품·서비스
- 새 고객·적용사례
- 성능·공정·운영방식의 의미 있는 진전
- 규제·정책·공급망 변화

후속기사라면 무엇이 새로 달라졌는지 본문에서 분명히 드러나야 한다.

## 8. 기사 작성
분량: 한글 약 1,300~1,700자.

기본 흐름:
`문제/변화 → 새 기술·제품·서비스 → 기존 방식과 차이 → 적용 의미 → 사업/운영 시사점 → 전망`

문체:
- 기술적으로 빈약하지 않되 일반 독자가 이해 가능
- 홍보문 금지
- 과도한 AI 만능론 금지
- 사실과 해석·전망 구분
- 핵심 메시지 하나

## 9. 파일명과 출처
TXT:
`YYMMDD.AutoGen.기사제목.txt`

파일명 문제 문자는 사용하지 않는다.
본문 하단에 기관/기업명, 자료명, 게시일, 원문 링크 또는 식별 가능한 출처를 표시한다.
그 아래 최신 AI 고지 규칙을 적용한다.

## 10. 대표이미지
기사마다 대표이미지 1장을 목표로 한다.

기본 기준:
- 사실적 산업현장 사진형
- 16:9
- 최종 1200×675 JPG
- 기사 핵심 장면 하나
- 큰 글자·인포그래픽·포스터·차트·기업 로고 금지

이미지 생성은 기본 1회, 명백한 오류 시 추가 1회만 허용한다.
**최대 2회**다.

상세 생성·저장 규칙은 `chatgpt/K-ARTICLE-IMAGE-RULES.md` v2.5 이상을 필수 적용한다.

## 11. 이미지 저장 — DIRECT ONE-SHOT 원칙
최종 이미지 한 장이 정상 확보되면 더 이상의 이미지 조사·품질시험·GitHub 사전검사를 중단한다.

저장 흐름은 다음 한 줄로 고정한다.

`최종 JPG 확정 → 최고 vN/SHA 1회 확인 → 동일 SHA면 기존 이미지 재사용 → 다르면 create_blob → create_tree → create_commit → update_ref → fetch_file 1회 → 종료`

정상 저장 경로에서 GitHub 관련 호출은 이미지 규칙 v2.5의 **7-call 상한**을 따른다.

같은 HEAD·tree·파일을 반복 조회하지 않는다.
이미 확보한 정보를 다시 검색하지 않는다.
도구 discovery는 실제 필요한 도구가 없는 경우에만 최대 1회 허용한다.

## 12. GitHub 저장소
- repository: `wskimgit/k-article`
- branch: `main`
- TXT/JPG: repository root

TXT는 UTF-8로 저장한다. 동일 내용이면 불필요한 update commit을 만들지 않는다.

JPG는 실제 JPEG 바이너리만 저장한다.

금지:
- 새 GitHub Actions workflow
- trigger 파일
- `.jpg.b64`
- Base64 chunk
- `_upload_*` 임시 폴더
- placeholder
- `main` force update
- base tree 없는 create_tree

과거 repository에 남은 레거시 workflow/trigger/chunk는 새 작업에서 사용하지 않는다.

## 13. 저장 실패 처리
정상 이미지가 확보된 후 저장 실패가 발생해도 이미지를 다시 만들지 않는다.

허용되는 저장 재시도는 **동시 변경에 따른 non-fast-forward 충돌 1회**뿐이다.
이 경우 같은 blob을 재사용하여 최신 HEAD/base tree에 다시 연결한다.

두 번째 저장도 실패하면 즉시:
`기사 저장 성공 / 이미지 저장 실패 / PARTIAL`
로 종료한다.

우회 저장을 시작하지 않는다.

## 14. ERRC — 1회만
최종 기사·이미지·경로를 한 번 검증한다.

실패 시:
- 수정 1회
- 재검증 1회

그 이후 추가 수정·추가 검증을 반복하지 않는다.

## 15. 작업 상태
### COMPLETE
기사 TXT와 대표이미지가 정상 저장되고 최소 검증 통과.

### PARTIAL
기사 TXT는 정상이나 이미지 생성 또는 저장 실패.

### HOLD
적합한 신규 기사 주제가 없어 기사 생성을 보류.

### ERROR
기사/저장 구조 자체를 정상 처리할 수 없는 치명적 오류.

모든 작업은 반드시 네 상태 중 하나로 끝난다.

## 16. HARD STOP
다음 조건 중 하나가 발생하면 추가 시도 없이 즉시 종료한다.

- 조사 확장 1회 소진
- 이미지 생성 2회 소진
- 이미지 저장 재시도 1회 소진
- 동일 SHA 확인
- GitHub 원격 재조회 성공
- ERRC 재검증 1회 소진

**성공 후 추가 확인을 하지 않는다. 실패 후 새로운 우회 경로를 찾지 않는다.**
