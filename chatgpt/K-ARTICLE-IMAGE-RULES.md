# K-ARTICLE 대표이미지 생성·저장 규칙 v2.4 — FROZEN

기준일: 2026-09-12
상태: FROZEN / K-ARTICLE-RULES v2.3에 대한 필수 이미지 규칙

## 1. 목적
대표이미지는 기사의 기술 내용을 모두 설명하는 도식이 아니라, **기사 주제와 직접 관련된 실제 산업현장을 빠르고 자연스럽게 보여주는 대표사진**을 목표로 한다.

이미지 품질은 유지하되 무한 재생성, 과도한 차별화 검사, 동일 이미지의 중복 버전 생성, 복잡한 GitHub 우회 저장을 방지한다.

핵심 원칙:
**좋은 이미지 1장 생성 → 필요 시 1회만 재생성 → 동일 SHA 확인 → 직접 GitHub 저장 → 1회 검증 → 종료**

## 2. 이미지 제작 기준
1. 고품질 생성형 이미지 모델을 사용한다.
2. 사실적인 산업현장 사진형을 기본으로 한다.
3. 기사 핵심 주제와 연결된 장면 하나만 표현한다.
4. 기술 내부 구조를 모두 도식화할 필요는 없다.
5. 16:9 비율, 최종 게시용 JPG는 1200×675로 정규화한다.
6. 기사 제목, 통계, 차트, 표, 화살표, 설명 패널, 뉴스페이지·포스터·인포그래픽을 넣지 않는다.
7. 실제 기업 로고·브랜드명·제품명·읽을 수 있는 UI 문구를 넣지 않는다.
8. 인터넷 기사 사진을 무단 복제하지 않는다.
9. 이미지 본체는 깨끗하게 생성하고, 필요한 AI 제작 고지는 정확한 후처리 또는 검증 가능한 방식으로 적용한다.

## 3. 기사와 이미지 관련성 판정
다음 조건이면 대표이미지로 인정한다.
- 기사에서 다루는 FAB·Subfab·클린룸·장비·Utility·정비·검사·물류·관제·연구환경 중 하나가 직접 보인다.
- 기사의 핵심 기술이 사용될 법한 실제 산업환경이 자연스럽다.
- 독자가 기사와 무관한 일반 사진으로 오해하지 않는다.

다음은 재생성 사유가 아니다.
- 촉매·센서·AI 알고리즘 같은 내부 기술이 사진에서 직접 보이지 않음
- 최근 기사와 산업 조명·금속설비 분위기가 일부 유사함
- 인원 수나 카메라 각도가 일부 겹침
- 설명 화살표나 텍스트가 없어 세부 원리가 한눈에 보이지 않음

## 4. 차별화 — 권고사항
최근 기사와 완전히 같은 대표사진을 반복적으로 재사용하지 않는다.
가능하면 사람 수, 복장, 구도, 배경, 핵심 대상 중 2개 이상을 다르게 한다.

그러나 차별화는 **강제 재생성 Gate가 아니다.**
기사와 직접 관련되고 품질이 정상이면 저장을 우선한다.

## 5. 생성 횟수 제한
### 기본
- 1차 이미지 생성 후 즉시 품질을 판정한다.
- 명백한 문제가 있을 때만 **1회 추가 재생성**한다.
- 한 기사에서 이미지 생성은 **최대 2회**다.

### 명백한 재생성 사유
- 기사와 전혀 무관
- 인포그래픽·포스터·뉴스페이지 형태
- 큰 글자·화살표·차트·기업 로고 삽입
- 사람·보호복·장비 구조의 심각한 왜곡
- 이미지 자체 생성 실패

### 2회 모두 실패
추가 생성하지 않는다.
TXT는 정상 저장하고:
`기사 저장 성공 / 이미지 생성 실패`
로 종료한다.

## 6. 생성과 저장을 분리한다
이미지가 정상 생성되면 **저장 오류 때문에 이미지를 다시 생성하지 않는다.**

GitHub 저장 또는 검증 실패 시 동일한 정상 이미지 바이너리를 재사용한다.
새로 그리는 것은 이미지 자체가 부적합한 경우에만 허용한다.

## 7. 파일 버전 및 동일 SHA 중복 방지
기존 파일을 덮어쓰지 않는다.

- 최초: `YYMMDD.AutoGen.기사제목.v1.jpg`
- 수정: `...v2.jpg`
- 재수정: `...v3.jpg`

저장 전 동일 기사 최고 `vN`을 확인한다.
TXT 논리 stem과 JPG에서 `.vN`을 제거한 논리 stem은 같아야 한다.
무버전 이미지는 레거시 `v0`로 취급한다.

### 동일 이미지 중복 방지
새로 확정한 JPG의 바이너리 또는 Git blob SHA를 현재 최고 버전 이미지와 비교한다.

- **동일하면 새 `N+1` 파일을 만들지 않는다.**
- 기존 최고 버전을 그대로 재사용한다.
- **다른 바이너리일 때만 `N+1`로 저장한다.**

이 규칙은 같은 그림을 `.v1`, `.v2`, `.v3`로 중복 보관하는 것을 방지한다.

## 8. GitHub 저장 — 직접·보존형 경로
최종 저장소:
- repository: `wskimgit/k-article`
- branch: `main`
- 위치: repository root

대표이미지는 실제 JPEG 바이너리로 직접 저장한다.

### 안전한 직접 저장 절차
1. 최종 JPG를 1200×675로 정규화한다.
2. 동일 기사 최고 `vN`과 SHA를 확인한다.
3. 동일 SHA이면 기존 최고 버전을 재사용하고 저장 단계를 종료한다.
4. 새 바이너리이면 `N+1` 경로를 결정한다.
5. 현재 `main` HEAD commit과 그 commit의 tree SHA를 확인한다.
6. JPEG를 Base64 전송 인코딩해 `create_blob(base64)`한다.
7. **현재 main tree를 `base_tree`로 사용하여** 새 이미지 경로만 추가한 tree를 만든다.
8. 현재 main HEAD를 parent로 새 commit을 만든다.
9. `update_ref(main)`은 **force 없이 fast-forward**로 수행한다.
10. main이 중간에 변경되어 ref update가 실패하면 최신 HEAD/tree를 다시 읽고 **동일 바이너리로 1회만 재시도**한다.
11. 최종 `.vN.jpg`를 `fetch_file(..., base64)`로 재조회한다.

### 금지
- `.jpg.b64`를 최종 이미지로 저장
- Base64 조각 파일을 repository에 남김
- 임시 upload 폴더 생성
- 이미지 한 장 저장을 위해 GitHub Actions workflow 생성
- trigger 파일 생성
- placeholder 저장
- 저장 실패 때문에 새 이미지를 재생성
- `main`을 force update
- base tree 없이 새 tree를 만들어 기존 repository 내용을 훼손

직접 저장이 1회 실패하면 동일 바이너리로 **1회만 재시도**한다.
두 번째 저장도 실패하면 `이미지 저장 실패`로 종료한다.

## 9. AI 제작 이미지 고지
`chatgpt/K-ARTICLE-RULES-AI-DISCLOSURE.md`의 최신 FROZEN 규칙을 적용한다.

가능하면 생성 모델에게 긴 한국어 문구를 그림 안에 직접 그리게 하지 않는다.
정확한 `생성형 AI 제작 이미지` 문구가 필요한 경우 **이미지 생성 후 우측 하단에 작은 후처리 텍스트로 적용**하는 것을 우선한다.

검증 기준:
- 문구가 정확함
- 기사 핵심 장면을 가리지 않음
- 읽을 수 있음
- 기업 로고처럼 보이지 않음

## 10. 저장 후 검증
최소 조건:
1. 정확한 `.vN.jpg` 경로 존재 또는 동일 SHA 기존 최고 버전 재사용
2. Base64 재조회 성공
3. JPEG 시작 시그니처 `FF D8`
4. 가능하면 종료 시그니처 `FF D9` 또는 decode 정상
5. 1200×675
6. blob SHA 확인
7. TXT와 이미지 논리 stem 일치
8. AI 제작 고지 규칙 충족
9. `.jpg.b64`, 임시 chunk, placeholder가 새 최종 산출물로 남지 않음

검증은 **1회** 수행한다.
검증 실패 시 저장 자체만 동일 바이너리로 1회 재시도한다.
이미지는 다시 생성하지 않는다.

## 11. egtech.php 표시 규칙
1. 기사 TXT 논리 stem과 같은 이미지 후보를 찾는다.
2. `vN` 중 가장 높은 버전을 표시한다.
3. 버전 파일이 없을 때만 무버전 레거시 이미지를 `v0` fallback으로 사용한다.
4. 같은 버전에서는 `jpg → jpeg → png → webp → gif` 순으로 우선한다.
5. 필요 시 `mtime-size` query로 브라우저 캐시를 방지한다.

동일 SHA 재사용으로 새 버전이 생성되지 않아도 기존 최고 버전을 정상 표시하면 된다.

추가 재생성·추가 우회 저장을 계속하지 않는다.

## 13. 최종 운영 절차
`기사 확정 → 이미지 1차 생성 → 명백한 오류 확인 → 필요 시 1회만 재생성 → 정상 이미지 확정 → 1200×675 JPG 정규화 → GitHub 최고 vN/SHA 확인 → 동일 SHA이면 기존 버전 재사용 → 새 바이너리이면 N+1 직접 저장 → 원격 재조회 1회 → 성공/실패 보고 → 종료`
